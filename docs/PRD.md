# 상식 퀴즈 게임 — Claude Code 구현 프롬프트 (3단계)

Oct 13, 2026 · @jihye

Doc을 3단계로 나눠 Claude Code에 그대로 붙여 넣을 수 있는 프롬프트로 정리했다. 각 단계는 앞 단계의 결과물 위에 쌓이며, PRD에서 제외한 기능(힌트, 난이도 선택, 로그인 등)은 넣지 않았다.

## 사용 방법

단계별 프롬프트를 순서대로 붙여 넣고, 각 단계의 확인 체크리스트를 통과한 뒤 다음 단계로 넘어간다.

1. PRD를 Markdown으로 내보내 프로젝트 폴더의 `docs/PRD.md`에 저장한다. 모든 프롬프트가 이 파일을 원문으로 참조한다.
2. 빈 폴더에서 Claude Code를 실행하고 1단계 프롬프트를 붙여 넣는다.
3. 체크리스트를 직접 확인하고, 문제가 있으면 같은 세션에서 고친 뒤 git 커밋한다.
4. 2단계, 3단계도 같은 방식으로 진행한다.

| 항목 | 선택 |
| --- | --- |
| 프론트엔드 | React + TypeScript + Vite |
| 테스트 | Vitest (+ 3단계 API는 Supertest) |
| 백엔드 (3단계) | Node.js + Express + SQLite |

PRD에 기술 스택이 없어 위 조합을 가정했다. 다른 스택을 쓰려면 각 프롬프트의 ‘기술 스택’ 줄만 바꾼다.

## 1단계: 핵심 퀴즈 시스템

목표는 서버 없이 브라우저에서 40문제를 끝까지 풀고 결과를 보는 MVP다. PRD의 F-01\~F-09를 다룬다.

```text
상식 퀴즈 게임의 1단계(핵심 퀴즈 시스템)를 구현해 줘.
요구사항 원문은 docs/PRD.md에 있어. 충돌하면 PRD를 따르고, 애매한 점은 구현 전에 물어봐 줘.

## 목표
서버 없이 브라우저에서 40문제를 끝까지 풀고 결과를 확인할 수 있는 MVP.

## 기술 스택
- React + TypeScript + Vite, 스타일은 CSS Modules
- 테스트는 Vitest
- 이번 단계는 프론트엔드만 (서버는 3단계에서 추가)

## 1.1 프로젝트 초기 설정
- Vite로 프로젝트 생성
- src/ 아래 components/, data/, game/, types/ 폴더 구성
- 게임 상태는 useReducer로 관리 (phase: 'start' | 'playing' | 'result')

## 1.2 문제 데이터 (src/data/questions.json)
- 한국사(history), 과학(science), 지리(geography), 예술과 문화(arts) 각 10문제, 총 40문제를 직접 작성
- 필드: id(예: hist-01), category, question(80자 이내), choices(보기 4개, 각 30자 이내),
  answerIndex(0~3), explanation(120자 이내)
- 작성 기준
  - 정답이 하나로 분명하고 출처로 검증 가능한 사실만
  - 오답 보기는 그럴듯하되 정답과 혼동되지 않게, '모두 맞음' 같은 보기 금지
  - 카테고리마다 쉬움 4 · 보통 4 · 어려움 2 비율
  - 인구·최신 기록처럼 바뀔 수 있는 정보는 출제하지 않음
  - 문제 교차 검증은 [docs/question-guidelines.md](question-guidelines.md)를 따름
- 로드 시 검증 함수 작성: 카테고리별 10문제, 보기 4개, answerIndex 범위, id 중복, 글자 수
- 작성한 40문제는 사람이 검수할 수 있도록 docs/questions-review.md에 표로도 정리

## 1.3 게임 진행 로직 (src/game/, 순수 함수)
- createGame(questions, nickname): 한국사 → 과학 → 지리 → 예술과 문화 순서,
  카테고리 안에서 문제 순서와 보기 순서를 무작위로 섞음 (보기를 섞으면 answerIndex도 갱신)
- answerQuestion(state, choiceIndex): 정답 판정, 한 번 고른 답은 변경 불가
- nextQuestion(state): 다음 문제로, 40번째 다음에는 결과 단계로
- getResult(state): 총점, 정답 수, 카테고리별 정답 수, 소요 시간(초)
- 점수: 정답 1개당 10점, 오답 감점 없음, 만점 400점
- 소요 시간: 첫 문제 표시부터 마지막 답 선택까지
- 무작위 함수는 주입받을 수 있게 해서 테스트에서 결과를 고정할 수 있게 해 줘

## 1.4 화면
- 시작: 제목, 규칙 요약(4개 카테고리 · 40문제 · 400점 만점),
  닉네임 입력(2~10자, 한글·영문·숫자만, 어기면 안내 문구), 시작 버튼
- 문제: 진행률 바, 카테고리 라벨, 문제 번호(예: 13/40), 현재 점수, 문제 본문, 보기 버튼 4개
- 피드백(문제 화면 위에 표시): 답을 누르면 0.3초 안에 정답은 초록, 오답은 빨강,
  오답이면 정답 보기도 강조, ✓/✗ 아이콘과 문구를 함께 표시, 해설 1~2문장, '다음 문제' 버튼
- 결과: 총점, 정답 수, 카테고리별 정답 수(예: 과학 7/10), 소요 시간, 다시 하기 버튼
- 모바일 세로 화면 기준, 화면 폭 360px 이상, 보기 버튼 높이 48px 이상

## 이번 단계에서 하지 않을 것
순위표, 서버, 오답 노트, 효과음, 카테고리 전환 화면, 키보드 단축키.
PRD 제외 항목(힌트, 난이도 선택, 로그인, 제한 시간)은 어느 단계에서도 넣지 마.

## 완료 조건
- 게임 로직 단위 테스트: 섞은 뒤에도 정답 판정이 맞는지, 점수 계산, 카테고리 순서,
  답 변경 불가, 40문제 후 결과 단계 전환, 문제 데이터 검증
- npm run test, npm run build 모두 통과
- 끝나면 파일 구조와 내가 직접 확인해 볼 방법을 요약해 줘
```

**확인 체크리스트**

- [ ] 40문제가 한국사 → 과학 → 지리 → 예술과 문화 순서로 출제된다
- [ ] 다시 하면 카테고리 안의 문제·보기 순서가 바뀐다
- [ ] 정답/오답 판정과 해설이 즉시 표시되고, 고른 답을 바꿀 수 없다
- [ ] 결과 화면의 총점·카테고리별 정답 수가 실제 풀이와 일치한다
- [ ] `docs/questions-review.md`로 40문제의 사실 관계를 사람이 검수했다

## 2단계: 결과 분석 · UX · 접근성 완성

목표는 1단계 게임을 PRD의 화면·UX·접근성 기준까지 끌어올리는 것이다. F-13(오답 노트), F-14(이탈 확인)과 7·8장 기준을 다룬다.

```text
상식 퀴즈 게임의 2단계(결과 분석 · UX · 접근성)를 구현해 줘.
1단계 코드 위에 쌓고, 요구사항 원문은 docs/PRD.md(특히 5·7·8장)야.
시작 전에 현재 코드 구조를 읽고, 바꿀 파일 목록을 먼저 알려 줘.

## 목표
한 판을 끝까지 편하게 풀고, 결과에서 무엇을 틀렸는지 복습할 수 있게 만든다.

## 2.1 진행 경험
- 카테고리가 바뀔 때 1초간 전환 화면 표시 (예: "과학 — 10문제")
- 정답·오답 효과음 추가, 켜고 끄는 토글 제공 (기본값 켜짐)
- 피드백 표시에 짧은 CSS 애니메이션 (전체 300ms 이내,
  prefers-reduced-motion이면 애니메이션 끄기)
- 게임 중 나가기(뒤로가기, 창 닫기, 처음으로 버튼)를 시도하면 확인 창 표시,
  중단한 게임은 결과로 치지 않음

## 2.2 결과 분석
- 결과 데이터에 문제별 기록 추가: questionId, 고른 보기, 정답 여부
- 카테고리별 성적을 가로 막대(0~10)로 표시하고 숫자도 함께 표기
- 오답 노트: 틀린 문제만 모아 문제, 내가 고른 답, 정답, 해설을 보여 줌
  (다 맞혔으면 "틀린 문제가 없습니다")

## 2.3 접근성
- 키보드만으로 전부 조작: 1~4키로 보기 선택, Enter로 다음 문제, 포커스 표시 선명하게
- 화면이 바뀔 때 포커스를 문제 본문으로 이동
- 스크린리더: 보기 버튼에 번호·내용 라벨, 피드백은 aria-live로 읽히게
- 정답/오답은 색만으로 구분하지 않기 (✓/✗ 아이콘 + 문구 유지)
- 텍스트·버튼 명도 대비 4.5:1 이상

## 2.4 반응형과 성능
- 360px 모바일부터 데스크톱까지 깨지지 않는 레이아웃, 데스크톱에서는 최대 폭 제한
- 효과음 파일은 작게 유지하고 미리 로드
- 프로덕션 빌드 기준 첫 화면 로딩 2초 이내(4G)를 목표로 번들 크기 확인

## 이번 단계에서 하지 않을 것
순위표와 서버(3단계). 힌트, 난이도 선택, 제한 시간, 게임 모드 추가는 PRD 범위 밖이야.

## 완료 조건
- 단위 테스트: 오답 노트 데이터, 키보드 입력(1~4, Enter) 처리, 카테고리 전환 표시 시점
- 접근성 자동 검사(axe 등)에서 심각한 오류 0건
- npm run test, npm run build 통과, 빌드 후 JS 번들 크기를 알려 줘
- 끝나면 바뀐 점과 내가 직접 확인해 볼 방법을 요약해 줘
```

**확인 체크리스트**

- [ ] 카테고리가 바뀔 때마다 1초 전환 화면이 나온다
- [ ] 마우스 없이 키보드만으로 한 판을 끝까지 풀 수 있다
- [ ] 효과음 토글이 작동한다
- [ ] 오답 노트에 틀린 문제만, 내 답·정답·해설과 함께 나온다
- [ ] 게임 중 나가기를 누르면 확인 창이 뜨고, 취소하면 이어서 풀 수 있다
- [ ] 휴대폰(360px)과 PC에서 레이아웃이 깨지지 않는다

## 3단계: 서버 채점과 순위표

목표는 기기 간에 공유되고 조작할 수 없는 순위표다. PRD의 F-10\~F-12와 8장의 데이터·보안·안정성 기준을 다룬다. PRD가 순위표를 서버에 두고 정답을 답 선택 후에만 보내도록 정했기 때문에, 로컬 스토리지가 아닌 서버 채점 방식으로 구성했다.

```text
상식 퀴즈 게임의 3단계(서버 채점과 순위표)를 구현해 줘.
1·2단계 코드 위에 쌓고, 요구사항 원문은 docs/PRD.md(특히 5·6·8장)야.
시작 전에 API 설계와 폴더 구조를 먼저 보여 주고 내 확인을 받아 줘.

## 목표
기기 간에 공유되고, 클라이언트에서 점수를 조작할 수 없는 순위표를 만든다.

## 기술 스택
- server/ 폴더에 Node.js + Express + TypeScript, 저장소는 SQLite(better-sqlite3)
- API 테스트는 Vitest + Supertest
- 개발 중에는 Vite 프록시로 /api를 서버에 연결, npm run dev 하나로 둘 다 실행

## 3.1 문제와 채점을 서버로 이동
- questions.json과 검증 함수는 서버로 옮기고, 클라이언트 번들에는 정답이 들어가지 않게 해
- 문제·보기 섞기, 정답 판정, 점수, 소요 시간 계산은 모두 서버가 한다
  (1단계의 순수 함수를 서버에서 재사용)

## 3.2 API
- POST /api/games {nickname}
  → gameId와 40문제(섞인 순서, 보기 포함, answerIndex·explanation 제외)
- POST /api/games/:id/answers {questionId, choiceIndex}
  → {correct, answerIndex, explanation, score}
  출제 순서대로만, 문제당 한 번만 받고 중복·순서 위반은 409
- POST /api/games/:id/finish
  → 40문제를 모두 답한 게임만 저장, 결과와 내 순위 반환
  점수·시간은 클라이언트가 보내지 않고 서버 기록으로만 계산
- GET /api/leaderboard?limit=10
  → 점수 내림차순, 동점이면 소요 시간 오름차순 상위 10명
- 중단된 게임은 순위에 기록하지 않고, 24시간이 지나면 삭제

## 3.3 저장 데이터 (PRD 6장 Score)
- scores: nickname, score(0~400), correctByCategory(JSON), durationSec, playedAt
- games: 진행 중 게임의 문제 순서, 보기 매핑, 답안, 시작 시각
- 개인정보는 수집하지 않음 (닉네임만)
- 같은 닉네임의 기록은 모두 저장 (PRD 미결 사항이라 시간 기간별 순위·최고 기록만 남기기로
  바꿀 수 있게 쿼리를 한 곳에 모아 줘)

## 3.4 부적절한 닉네임과 기록 관리
- 서버에서 닉네임 규칙(2~10자, 한글·영문·숫자)과 비속어 목록(server/data/banned-words.txt) 검사
- 기록 삭제용 CLI 스크립트: npm run delete-score -- <id> (관리자 화면은 만들지 마)

## 3.5 클라이언트 변경
- 게임 진행을 위 API로 교체, 피드백은 응답을 받은 뒤 표시하되 0.3초 안에 나오게
  (응답 대기 중에는 고른 보기를 바로 누른 상태로 표시)
- 시작 화면의 '순위표 보기', 결과 화면의 상위 10명 순위표와 내 순위(예: 37위), 내 기록 강조
- 네트워크 오류로 저장·답안 전송에 실패하면 오류 문구와 재시도 버튼

## 완료 조건
- API 테스트: 정상 플레이 저장, 동점 정렬, 중복 답안 409, 40문제 미만 finish 거부,
  클라이언트가 score를 보내도 무시, 비속어 닉네임 거부, /api/games 응답에 정답이 없는지
- 클라이언트 빌드 결과물에 explanation·answerIndex 문자열이 없는지 확인
- npm run test, npm run build 통과
- 끝나면 실행 방법, 배포 시 필요한 환경 변수, 내가 직접 확인해 볼 방법을 요약해 줘
```

**확인 체크리스트**

- [ ] 두 기기(또는 두 브라우저)에서 푼 기록이 같은 순위표에 보인다
- [ ] 동점일 때 더 빨리 푼 사람이 위에 있다
- [ ] 상위 10위 밖이어도 결과 화면에 내 순위가 나온다
- [ ] 개발자 도구 네트워크 탭에서 답을 고르기 전에는 정답이 보이지 않는다
- [ ] 서버를 재시작해도 순위표가 유지된다
- [ ] 중간에 나간 게임은 순위표에 없다
- [ ] 네트워크를 끊고 답을 고르면 재시도 버튼이 나온다

## 4단계: 선생님 모드 — 로그인과 문제 교체

목표는 선생님이 웹에서 로그인해 출제 문제를 후보 문제와 바꾸는 것이다. 지금은 `npm run swap-question` CLI로만 바꿀 수 있고, 바꾼 뒤 서버를 재시작해야 한다. 이번 단계는 최소 범위(로그인 + 교체)만 다루고, 성적 화면·학생 명단 DB 이전 등은 후속 이슈로 미룬다.

```text
상식 퀴즈 게임의 4단계(선생님 모드: 로그인과 문제 교체)를 구현해 줘.
1~3단계와 후보 문제·교체 CLI(server/src/questionBank.ts) 위에 쌓는다.
시작 전에 API 설계와 화면 흐름을 먼저 보여 주고 내 확인을 받아 줘.

## 목표
선생님이 공용 비밀번호로 로그인해, 서버를 재시작하지 않고 출제 문제를 같은 카테고리·난이도의 후보 문제와 바꾼다.

## 4.1 선생님 로그인 (서버)
- 공용 비밀번호 하나를 환경 변수 TEACHER_PASSWORD로 받는다. 설정하지 않으면 선생님 API는 모두 404
- POST /api/teacher/login → 세션 쿠키(httpOnly, SameSite=Strict, 운영에서는 Secure), POST /api/teacher/logout
- 세션은 SQLite에 만료 시각과 함께 저장(예: 8시간). 비밀번호 비교는 timingSafeEqual
- 로그인 실패가 짧은 시간에 반복되면 잠시 거부(429)
- 선생님 API는 세션이 없거나 만료되면 401

## 4.2 재시작 없는 문제 교체 (서버)
- GET /api/teacher/questions: 출제 문제와 후보 문제(정답·해설 포함, 로그인한 선생님에게만)
- POST /api/teacher/swap { bankId, candidateId }: questionBank.ts의 교체 로직 사용, 다른 칸끼리는 400
- 교체 후 서버 메모리의 문제 목록을 바로 바꾼다. 새 게임은 출제 문제에서만 뽑고,
  진행 중인 게임은 출제 + 후보 문제 전체에서 id로 찾아 교체 전에 시작한 게임도 원래 문제로 채점한다
- 파일은 임시 파일에 쓴 뒤 이름을 바꿔 저장(중간 실패 시 원본 유지)

## 4.3 선생님 화면 (클라이언트)
- 시작 화면 구석의 '선생님' 링크 → 로그인 화면 → 문제 교체 화면 → 로그아웃
- 교체 화면: 카테고리·난이도별로 출제 문제와 같은 칸의 후보 문제를 나란히 보여 주고, 확인 창을 거쳐 교체
- 2단계 접근성 기준(키보드 조작, 포커스, axe 검사)을 지킨다
- 학생용 화면과 API에는 지금처럼 답을 고르기 전에 정답이 보이지 않아야 한다

## 이번 단계에서 하지 않을 것
- 선생님 계정 여러 개, 비밀번호 변경 화면
- 학생 명단 DB 이전, 성적·비교·약점 화면, 문제별 답안 장기 보관, 선생님 모드 계산의 코드 이전(후속 이슈)
- 기록 삭제 화면(npm run delete-score 유지)

## 완료 조건
- API 테스트: 비밀번호 미설정 404, 로그인 없이 401, 틀린 비밀번호 401, 반복 실패 429, 세션 만료,
  교체 성공 후 새 게임에 반영, 교체 전에 시작한 게임이 끝까지 저장됨, 다른 칸 교체 400
- 학생용 API 응답과 클라이언트 번들에 정답이 없는지(기존 검사 유지)
- npm run test, npm run build 통과
- 끝나면 실행 방법, 필요한 환경 변수, 내가 직접 확인해 볼 방법을 요약해 줘
```

**확인 체크리스트**
